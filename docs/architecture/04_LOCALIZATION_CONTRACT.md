# 04 — LOCALIZATION ARCHITECTURE CONTRACT

## 1. LOCALIZATION SYSTEM INVENTORY

NexaBiz is natively multilingual (`en` and `ar`). The localization infrastructure consists of:

| Component | File / Location | Responsibility |
| :--- | :--- | :--- |
| Config File | `l10n.yaml` | Configures Flutter's `gen-l10n` tool (`arb-dir: lib/l10n`, `template-arb-file: app_en.arb`). |
| English ARB | `lib/l10n/app_en.arb` | Source template translation catalog for English messages. |
| Arabic ARB | `lib/l10n/app_ar.arb` | Mandatory Arabic translation catalog matching all English keys. |
| Generated API | `lib/l10n/app_localizations.dart` | Strongly-typed localization class generated by Flutter l10n. |
| Locale Controller | `lib/app/localization/app_locale_controller.dart` | Global controller managing active `Locale`, `SharedPreferences` persistence, and language toggling. |

---

## 2. NON-NEGOTIABLE LOCALIZATION RULES

### Rule 4.1: Zero Hardcoded User-Visible Strings
- Hardcoded user-visible string literals inside widgets, pages, dialogs, sheets, buttons, titles, errors, or tooltips are **STRICTLY FORBIDDEN**.
- This applies to **BOTH** English literals (`Text('Save')`) and Arabic literals (`Text('حفظ')`).

```dart
// ALLOWED: Canonical localization API usage
Text(l10n.saveButton)

// FORBIDDEN: Hardcoded English or Arabic string literal
Text('Save') // VIOLATION
Text('حفظ')  // VIOLATION
```

### Rule 4.2: Mandatory Complete Locale Coverage
NexaBiz officially supports `en` and `ar`.
- Every NEW localization key added to `app_en.arb` **MUST** simultaneously be added to `app_ar.arb`.
- PRs or code changes that add keys to English without corresponding Arabic translations are **INVALID**.

### Rule 4.3: Technical Identity vs User-Facing Representation
Do **NOT** localize technical identity strings:
- Route paths (e.g. `/dashboard`, `/services`)
- Database table or column names
- Technical enum values or preference keys (`nexabiz_user_locale`)
- Asset paths (`assets/fonts/Cairo/`)
Localize **ONLY** user-visible text rendered in presentation code.

### Rule 4.4: Dynamic Placeholders over Sentence Concatenation
Dynamic localized messages must use parameterized placeholders defined in the ARB format:

```json
"welcomeUser": "Welcome back, {userName}!",
"@welcomeUser": {
  "placeholders": {
    "userName": { "type": "String" }
  }
}
```

Do **NOT** construct sentences using string concatenation (`'Welcome ' + userName`).

---

## 3. LOCALE SWITCHING & STACK PRESERVATION

- Changing the application locale (e.g. English -> Arabic) via `AppLocaleController.toggleLanguage()` or `setLocale()` updates the UI dynamically.
- Locale changes **MUST PRESERVE** the active navigation stack.
- If navigation history is `A -> B -> C` prior to language switch, the active route remains `C` post-switch, and Back unwinds `C -> B -> A`.

---

## 4. LOCALIZATION PROCEDURE WORKFLOW

```text
Identify required user-visible string
       ↓
Define semantic key in lib/l10n/app_en.arb
       ↓
Add exact Arabic translation in lib/l10n/app_ar.arb
       ↓
Run `flutter gen-l10n` (or `flutter pub get`) to rebuild generated code
       ↓
Consume `AppLocalizations.of(context).yourKey` in widget
       ↓
Verify rendering in LTR (en) and RTL (ar)
```

## 5. NEW USER-VISIBLE STRING CHECKLIST

```text
NEW USER-VISIBLE STRING CHECKLIST

[ ] Search existing keys in lib/l10n/app_en.arb for reusable message.
[ ] Define semantic camelCase key name (e.g. invoiceTotalAmount).
[ ] Add key & description entry to lib/l10n/app_en.arb.
[ ] Add corresponding key & translation entry to lib/l10n/app_ar.arb.
[ ] Use parameterized placeholders if string contains dynamic variables.
[ ] Execute code generation (flutter gen-l10n).
[ ] Access message via AppLocalizations.of(context).key.
[ ] Verify layout text scaling and wrapping in Arabic (RTL).
```
